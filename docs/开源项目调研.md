# GitHub 开源项目调研

> 核对日期：2026-09-16。商业化广告审核中台通常是公司的核心内部系统，GitHub 上很少存在可直接复刻的“大厂完整方案”。本文选择公开的相邻能力进行组合学习，不把任何项目描述成某家公司的内部审核系统。

## 调研结论

审核中台至少需要五类能力共同工作：

1. 审核工作台与案件流转。
2. 可版本化的业务规则和访问策略。
3. 文本、图片、视频、音频、URL、主体和交易信号。
4. 人工标注、质量复核、模型评测与数据集管理。
5. 灰度发布、决策日志、证据追溯和运营分析。

不存在一个开源项目完整覆盖这些能力，因此本仓库只借鉴接口和治理模式，不直接拼接成生产系统。

## 可复用的设计模式

### 规则、模型与政策分层

- 政策层描述禁止、限制和需要证明的业务事实。
- 规则层把事实转换为确定性条件，可版本化和回放。
- 模型层提供不确定信号、置信度和解释，不直接拥有政策结论。
- 编排层把多个信号变成自动通过、自动拦截或人工审核路由。

### 人工审核是数据生产系统

审核员不只是处理队列，也在生产高价值标签。必须记录看到的内容版本、证据、可选政策、最终决定、用时、修改历史和信心等级。复审与申诉结果应回流评测集，但需要样本治理和 Owner 审批。

### 决策日志不可变

规则、模型和人工决定都写入追加式事件表；业务状态表可以更新当前状态，但历史决定、命中原因和执行结果不能覆盖。更正使用新事件并关联被更正事件。

### 发布需要影子和回放

新规则或模型先在历史 Golden Set 回放，再在实时流量影子运行，然后小比例灰度。对通过率、漏放、误杀、队列量、SLA 和风险调整收益设置联合门禁，并准备 Kill Switch。

## 不直接采用的做法

- 不复制任何公司政策库、阈值或绕过检测信息。
- 不让规则脚本访问应用对象、网络、文件系统或密钥。
- 不把模型概率直接映射成永久封禁、资金冻结等高影响动作。
- 不以审核员处理量作为唯一绩效指标，避免诱导草率判断。
- 不把申诉翻案简单视为审核员错误；需要区分证据新增、政策变化、规则缺陷和判断差异。
- 不在没有许可复核时复制第三方源码或模型权重。
